Core bridge: how OpenImport writes data¶

OpenImport never writes catalog, customer or stock tables itself. It prepares rows (read the file, map columns, transform values, filter rows) and hands them to Magento's own import engine, the one behind System › Data Transfer › Import. Whatever core would write for an equivalent CSV file is what OpenImport writes.

The pieces¶

Class Job
Model\Source\MappedSource Core's AbstractSource over OpenImport's prepared rows. No temporary CSV file: core pulls rows from a generator. Missing columns become empty cells, like an empty CSV cell ("leave unchanged").
Model\Bridge\CoreImport Core's Import model plus getBunchIds(): the importexport_importdata rows this import validated (2.4.9 has getValidatedIds(), 2.4.7 and 2.4.8 do not).
Model\Bridge\CoreImporter Validate, then (live runs only) add a core import history row, import, invalidate the entity's indexers, and always remove this run's bunches.
Model\Bridge\ImportRequest / ImportResult / RowError What to run, and what came back (counts, errors with 0-based row positions, history id, time).

Why the bunches are removed¶

Core validation stores the validated rows in importexport_importdata and later imports the bunches whose ids the entity adapter collected. A dry run validates and stops, so its bunches would stay in the table. They are deleted by id at the end of every run, dry or live, and also when core throws.

Import history¶

Core's import updates the most recent history row of the current admin user (2.4.7, 2.4.8) or the row named in _import_history_id (2.4.9). A live OpenImport run adds its own history row right before the import and passes its id, so core's updates land on OpenImport's row on every version, never on someone else's import. The run appears under System › Data Transfer › Import History with its summary. The history row has no downloadable file yet (M1 writes the mapped rows there).

Evidence¶

Test/Integration/Bridge/CoreBridgeTest.php imports the same rows twice, once through core's CSV source (the admin path) and once through MappedSource, and compares the results field by field:

  • simple products: new products with stock, special price, HTML description, disabled status, "Not Visible Individually", a store-view row; updates including __EMPTY__VALUE__; Replace and Delete;
  • customers;
  • dry run: nothing written, no bunch left behind;
  • invalid rows with "skip errors": reported with their 0-based position, same outcome as core's CSV import; nothing imported with "stop on error";
  • import history row written and completed.

What the spike found¶

  1. Core's error aggregator is shared. ProcessingErrorAggregator is a DI singleton. Core runs one import per admin request; OpenImport runs many per process (cron, CLI). Without clear() before each run, errors of earlier runs counted against the next run and stopped valid imports. CoreImporter clears it first.
  2. Store-view rows of new products need attribute_set_code and product_type. Core validates every row of a product that is new in the file as a new product. A store-view row with only sku, store_view_code and name is refused ("Product Type is invalid or not supported"), through the CSV source as well. OpenImport's store-view expansion (M1) copies both onto the rows it generates.
  3. An empty cell in a required attribute's column is an error, also for existing products. A file with a name or price column must fill it on every row. The mapping preview (M1) flags such rows before core sees them.
  4. Validated bunches stay in importexport_importdata unless removed. Removed by id after every run.
  5. Core's history update targets "the last row of this admin user" (2.4.7, 2.4.8) or _import_history_id (2.4.9). Adding OpenImport's own row right before the import and passing its id works on all three.
  6. Core reports 0-based positions of the rows it received. Mapping back to source line numbers is M1 (rows can be filtered out or expanded into store-view rows on the way).
  7. "Skip rows with errors" skips everything after one critical error. Core's row errors are critical by default, and the product, customer and other entities stop saving every row once the aggregator holds a critical error (hasToBeTerminated()), even with the skip-errors strategy, while the import still reports success (found in M1). With Skip rows with errors, OpenImport leaves the rows core rejected out (SkipRowsSource), validates the rest again and imports that; errors of every pass still point at the original rows. At most four validation passes; a critical error without a row stops the run with nothing imported.
